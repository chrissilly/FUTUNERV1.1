## 0. TL;DR for Sean

The cloud today is **device-centric**: a dongle owns an `auth_token`,
and license state (`paid`/`revoked`) lives as columns on the `devices`
row. There is **no concept of a customer/user**. The handoff asks for a
**user-centric** model: `users` → `vehicles` → `licenses`, with a web
dashboard customers log into.

Bolting a user model onto a device-centric server is clean *except for
one real fork*: **license state would then live in two places** — the
dongle still reads `devices.paid` (backward-compat critical, R4), but
the customer/billing truth wants to live in the new `licenses` table.
How those two reconcile is the one decision with no obviously-correct
answer. It is decision **D1** in §6. The other three (data layer,
session model, UI rendering) have a clear recommendation each.

Nothing here blocks a clean extension — there are **no wire-protocol or
schema bugs** that prevent moving forward (no PHASE-0 HALT trigger
tripped). There are, however, **two hygiene gaps to fix before any
commit** (§4: gitignore gap C6, and the main.py size/Rule-6 split C9),
and **one downstream blocker** to flag now so it is not a surprise at
PHASE 5: P-74's `ecu_var_db_<boxcode>.json` output **does not exist
yet** (only the parser shipped today) — PHASE 5 will HALT on it unless
it lands first (§7).

## 2. Existing schema (5 tables)

From `init_db()` + the idempotent `ALTER TABLE` license migration.
**There are NO foreign-key constraints declared anywhere today.** All
cross-table references are by convention only (see "soft ref" below).
`db()` sets `PRAGMA foreign_keys = ON` per connection, but with zero FK
constraints declared it is currently a no-op.

### 2.1 `devices` (PK `mac`)
```
mac TEXT PK | auth_token TEXT NOT NULL UNIQUE | vin TEXT | boxcode TEXT
owner_name TEXT | owner_email TEXT | dealer_id TEXT
active_firmware TEXT  -- soft ref → firmware.build_hash
active_cal      TEXT  -- soft ref → calibrations.filename
last_seen INTEGER | created_at INTEGER | ethanol_random INTEGER
paid INTEGER DEFAULT 0       -- added via ALTER (SCALE_ARCH §6)
revoked INTEGER DEFAULT 0    -- added via ALTER
revoked_reason TEXT          -- added via ALTER
```
Indexes: PK on `mac`, UNIQUE on `auth_token`. No others.

### 2.2 `firmware` (PK `build_hash`)
`build_hash PK | filename NOT NULL | build_number | size_bytes | sha256 | notes | created_at | is_release DEFAULT 0`

### 2.3 `calibrations` (PK `filename`)
`filename PK | boxcode NOT NULL | version | size_bytes | sha256 | ethanol_bit_count | notes | created_at`

### 2.4 `device_log` (PK `id` AUTOINCREMENT)
`id PK | mac (soft ref → devices.mac) | ts | event | detail`
No index on `mac` — `GET /admin/log/{mac}` does a full scan + sort. Fine
at current scale; note for later.

### 2.5 `wot_logs` (PK `id` AUTOINCREMENT) — P-67
`id PK | mac NOT NULL (soft ref → devices.mac) | vin | uploaded_at NOT NULL | file_path NOT NULL | byte_count NOT NULL`
Index: `idx_wot_logs_mac_ts (mac, uploaded_at DESC)`. **This is the
table PHASE 4 reads from.** Files live under `WOT_LOG_DIR/<mac-no-colons>/<ts>_<hex>.csv.gz`.

## 3. Auth models (3, all token/key lookups — no sessions today)

1. **Bearer** (`device_for_token`): `Authorization: Bearer <token>` →
   row where `auth_token = token`. 401 on missing/empty/unknown.
2. **X-Device-Auth** (`device_for_x_device_auth`): bare token, no
   prefix. Same lookup. Exists only because the dongle's telemetry
   uploader sends a bare header (P-67). **Duplicate logic** of #1 minus
   the prefix parse — candidate to fold into one helper, but R4 says
   don't change wire shape, so leave both; just share the DB lookup.
3. **Admin** (`require_admin`): `X-Admin-Key` vs `ADMIN_API_KEY` env via
   `hmac.compare_digest`. 500 if key unset, 403 if mismatch.

**There is no session/cookie machinery at all.** The customer dashboard
(PHASE 2/5) introduces the first browser-session surface. It must not
reuse device Bearer tokens (those are per-dongle secrets in NVS, not
human credentials).

## 4. Coupling risks (where customer code meets dongle code)

Ordered by consequence. C1–C3 are design forks; C4–C10 are hygiene/ops.

- **C1 — License double-source (THE fork → decision D1, §6).** The
  dongle reads `devices.paid`/`devices.revoked` via `GET /api/v1/license`
  (R4: shape AND data source are load-bearing — firmware trusts it). The
  customer model wants a per-vehicle `licenses` table with a state
  machine (trial→paid→expired→revoked). If a license expires in
  `licenses` but `devices.paid` still says 1, the dongle keeps working.
  These MUST reconcile. Options in §6/D1.

- **C2 — Identity duplication.** `devices.owner_name`/`owner_email` are
  free-text today (set by admin at enroll). The new `users.email` is the
  real account identity. When a user claims a vehicle, do we backfill
  `devices.owner_email` from the user (denormalized, convenient for the
  existing admin list) or leave it and treat `users` as authoritative?
  Recommendation: leave `devices.owner_*` as legacy display fields,
  treat `users` as truth, and (optionally) backfill `owner_email` on
  claim for admin-list continuity. Low-risk; documented in D1's wake.

- **C3 — `vehicles.dongle_mac` → `devices.mac` (the "marry" step).** The
  claim flow (PHASE 3) binds a vehicle to an already-enrolled device by
  MAC. Should `dongle_mac` be a hard FK to `devices.mac`? If yes, a
  customer can only claim a MAC SRM has enrolled (prevents typo-squatting
  a stranger's future MAC; claim of unknown MAC → 404/409). If no, a
  user could pre-claim a MAC that doesn't exist yet. **Recommendation:
  hard FK `dongle_mac → devices(mac) ON DELETE RESTRICT`**, claim of an
  unknown MAC returns 404. This is a sub-decision folded under D1 unless
  Sean wants it separated.

- **C4 — Test isolation fragility.** Both `test_smoke.py` and
  `test_telemetry_log.py` monkeypatch module globals on `src.main`
  (`DATA_DIR`, `DB_PATH`, …) at import time and call `init_db()`. pytest
  imports all test modules before running any test, so **last import
  wins** for the shared globals; the suites only coexist because they use
  disjoint MAC namespaces (`30:…`, `aa:…`, `40:…`, `50:…`, `60:…`).
  Adding 6 more test files this way will eventually collide. **Strong
  recommendation: add `tests/conftest.py` with a fixture that gives each
  test its own tempdir + DB** (monkeypatch via fixture, not import-time),
  and migrate new tests to it. Old tests keep passing untouched (R5).

- **C5 — No FKs today, but new tables WILL enforce.** Because `db()` sets
  `PRAGMA foreign_keys = ON`, the moment we declare FKs on the new tables
  they are enforced for connections that touch them. SQLite **cannot
  `ALTER TABLE ADD` a FK** — every FK + `ON DELETE` must be declared at
  `CREATE TABLE`. Since the new tables are greenfield, this is fine; just
  noting we can't retrofit FKs onto `devices` (so `vehicles.dongle_mac →
  devices.mac` is the only cross-old/new FK, declared on the new side).

- **C6 — gitignore gap (FIX BEFORE ANY COMMIT — R3).** `cloud/data/` and
  `cloud/wot_logs/` are **not** gitignored (`git check-ignore` returns
  nothing). The README even says "data/ ← gitignore in real deploy" but
  it was never added. Today both dirs are empty so nothing leaked, but
  running the app locally creates `data/srm.db` (now containing customer
  emails + password hashes once PHASE 2 lands) and `wot_logs/` (customer
  telemetry). A stray `git add` would commit proprietary/customer data.
  **PHASE 1 first action: add `cloud/.gitignore` for `data/`, `wot_logs/`,
  `__pycache__/`, `.pytest_cache/`, `*.db`.**

- **C7 — README ↔ Caddyfile path-prefix drift.** README curl examples
  use `https://…/fut/health`, but `Caddyfile` reverse-proxies the bare
  domain root (`sillyrabbitmotorsport.com → 127.0.0.1:8000`), so the real
  path is `/health`. Not my file to fix unilaterally, but it directly
  affects PHASE 5: **template link targets must be root-relative** (`/app/…`,
  `/api/v1/user/…`), which works under the current Caddyfile. Flagged so
  the doc drift gets reconciled (Rule 7/8/9 spirit) — surfaced, not
  silently patched.

- **C8 — WOT_LOG_DIR spec gap (known, P-67).** Spec said `/cal/wot_logs`;
  implementation is ROOT-relative `cloud/wot_logs` (env-overridable),
  because the literal host path doesn't exist inside the container. Already
  flagged to Sean in status-2026-05-23. PHASE 4 reads from the real dir;
  no action beyond awareness.

- **C9 — `main.py` is 796 lines (Rule 6 smell, R1 mandate).** Already
  over the ~500-line line. The handoff R1 *requires* the split into
  `auth.py`/`vehicles.py`/`licenses.py`/`logs.py`/`views.py`/`admin.py`
  with `main.py` shrinking to app wiring + lifespan. I'll do the split
  incrementally per phase (move admin endpoints out in PHASE 6) rather
  than one big-bang refactor, to keep each phase's diff reviewable and
  old tests green throughout (R5). **This means main.py stays >500 until
  PHASE 6** — calling that out so it isn't read as a new violation.

- **C10 — SQLite write-lock under new relational load.** One connection
  per request, no pool, no WAL. Adds joins (user→vehicle→license→logs)
  and the first concurrent **writes** from humans (signup, claim) on top
  of dongle writes. At a $5-VPS / handful-of-customers scale this is
  fine, but a single writer lock can surface `database is locked` under
  concurrency. **Cheap mitigation: enable WAL + a busy_timeout in `db()`**
  (`PRAGMA journal_mode=WAL; PRAGMA busy_timeout=5000`). Low-risk, helps
  the existing dongle path too. Proposed for PHASE 1, flagged here.

Each new endpoint group is a FastAPI `APIRouter` in its own module,
included by `main.py`. This satisfies R1 (≤500 lines/file) without a
big-bang rewrite and keeps every phase's diff small.

**Customer route namespace:** `/api/v1/user/*` (auth, vehicles,
licenses, logs) + `/app/*` (HTML). Admin stays `/admin/*`. Device stays
`/api/v1/device/*` + `/api/v1/license` + `/api/v1/telemetry/log` —
**untouched** (R4).

### 5.1 License reconciliation (the recommended shape for D1)

`licenses` table is the **customer/billing source of truth**
(per-vehicle, with the state machine). A single function
`reconcile_device_license(mac)` in `licenses.py` projects the *effective*
state of a vehicle's current license down onto the legacy
`devices.paid`/`devices.revoked` columns. It is called whenever a
license changes (admin set, Stripe stub, renew, expiry sweep). Result:

- `GET /api/v1/license` and the dongle stay **byte-for-byte unchanged**
  (R4) — they still read `devices.paid`, which is now a *projection*.
- `licenses` carries tier/dates/token/history the dongle never needed.
- One reconcile function = one place where the two representations meet.

The honest alternative (rewrite `GET /api/v1/license` to JOIN
device→vehicle→license live) is in D1 below. Both are viable; this is a
genuine fork, so it's Sean's call.

## 6. 🛑 DECISIONS NEEDED — sign-off gate

Each decision lists options with trade-offs (R7). My recommendation is
marked ★. **D1 is the one with no clean answer** — both options are
presented without a ★ lean beyond a mild preference.

### D1 — License source of truth / reconciliation (the core fork)
- **Option A — `licenses` authoritative + projection onto `devices`
  (reconcile fn).** Dongle endpoint untouched (R4 safest); one sync
  point; mild denormalization (paid stored twice, kept in lockstep by
  one function). Risk: if a code path forgets to call reconcile, drift.
- **Option B — `devices.paid` stays the only truth; `licenses` is a
  thin audit/history mirror.** Zero drift risk on the dongle path
  (single source). But the customer-facing state machine (trial/expiry
  dates) then has nowhere authoritative to live — defeats much of S3.
- **Option C — Rewrite `GET /api/v1/license` to JOIN live from
  `licenses`.** Single source of truth, no projection. Risk: changes the
  device endpoint's *data source* (not its wire shape) — a subtle R4
  surface change the firmware can't see but we must test hard; also adds
  a 3-table join to the dongle's hottest read.
- *Mild preference:* **A** (keeps R4 ironclad, isolates the messy part
  to one function). Sub-decision C3 (hard FK on `dongle_mac`) rides here
  unless you want it separate.

### D2 — Data access layer
- ★ **Raw SQL + a shared `db.py` helper.** Matches the existing 800
  lines exactly (zero new pattern to learn/audit), no new dependency,
  and PHASE 1 wants hand-written reversible SQL migrations anyway.
  Trade-off: hand-written joins are more error-prone than an ORM and
  there's no automatic FK/migration tooling.
- **SQLAlchemy ORM (+ Alembic).** FK integrity, relationships, and
  migrations "for free"; nicer for the new relational shape. Trade-off:
  a heavy new dependency, a *second* data-access idiom alongside the
  existing raw SQL (drift), and overkill for SQLite on a $5 VPS.
- *Recommend ★ raw SQL* for consistency + auditability; revisit if/when
  the SCALE_ARCH PostgreSQL move happens.

### D3 — Session model
- ★ **Server-side sessions (`sessions` table) in an HttpOnly, Secure,
  SameSite=Lax cookie.** Revocation is a hard requirement here (logout,
  password reset, license revoke should kill access) and a DB session
  revokes by `DELETE`/expiry — trivial and honest. The `sessions` table
  is already in the PHASE 1 schema.
- **JWT.** Stateless, no session table reads. Trade-off: revocation
  needs a blocklist table or key rotation anyway — so it's *not* truly
  stateless for our needs, and "stateless JWT" would be a lie given we
  need revoke. More moving parts for no win at this scale.
- *Recommend ★ server-side sessions.*

### D4 — Customer UI rendering
- ★ **Server-rendered Jinja2 templates + minimal JS.** No build step, no
  bundler, served from the same FastAPI process; testable with `requests`
  (the handoff explicitly wants `test_views.py` to be requests-based HTML
  smoke, NOT Playwright). Reuses one process, easy to audit — matches the
  existing "≈400 LOC, easy to audit" ethos. The one JS island is the
  gauge-replay chart (Chart.js via a single documented CDN).
- **Static SPA (React/Vue/etc.).** Nicer interactivity. Trade-off: a
  third front-end surface (after the dongle's two HTML UIs) → more drift;
  a build/bundle pipeline; and it breaks the requests-based test plan.
- *Recommend ★ server-rendered Jinja2.*

### Secondary decisions (lower consequence — I'll default unless you object)
- **Password hashing:** default **argon2id** (`argon2-cffi`) — current
  OWASP first choice; bcrypt is the fallback if you'd rather not add the
  dep. Either is fine; never plaintext/MD5/SHA1.
- **Stripe stub:** I'll stub an interface (`create_checkout_session`,
  `handle_webhook`) that logs + returns mock objects, with the
  `stripe_events` table ready for real webhook ingest. **But tiers,
  pricing, and trial length need your input** (HALT trigger) before
  PHASE 3 finalizes the renew endpoint. Not needed to start PHASE 1/2.
